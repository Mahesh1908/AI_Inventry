  Current understanding

  A cement company needs an order-fulfilment system across 3 fixed warehouses
  (WH-A/B/C). On order submission, the system runs a deterministic decision
  chain — customer eligibility → product/stock existence → aggregate stock
  sufficiency → allocation-by-earliest-dispatch-date → delivery-date feasibility
  — and either releases the order (with per-warehouse allocations and inventory
  deduction, all in one transaction) or persists it as blocked with a specific
  reason code. Results are retrievable by order id, idempotently on
  resubmission. Stack: React+TS frontend, Node/Express+TS backend, MSSQL.
  Nothing exists in the repo yet — this is a from-scratch build.

  The spec itself already encodes the answers to most ambiguity classes
  (boundary rule for delivery date is inclusive per A-02/T-09, blocked orders
  are terminal per A-05, customer_type is a no-op field per A-03, etc.), so I
  did not re-derive those — I took them as fixed unless flagged below.

  Questions and provisional assumptions

  O-01 — Past promised_delivery_date: validation error or business block?
  Impact: determines whether a past date returns HTTP 400 (nothing persisted) or
  is persisted as BLOCKED DELIVERY_DATE_NOT_MET. This changes what T-16-style
  tests expect and whether FR-02's validator needs a "not in the past" rule.
  Question: Should structural validation reject a past promised_delivery_date,
  or should it always be allowed through to the business rule engine?
  Provisional assumption (reversible): treat it as a business-rule failure, not
  a validation error — a past date will almost always fail
  expected_delivery_date <= promised_delivery_date naturally, so no special
  validation code is needed. This is the simpler default and is easy to add a
  validation-layer check for later if you decide otherwise.

  O-02 — Quantity precision: whole bags or decimal MT?
  Impact: affects UI input step/formatting and whether display should round;
  does not affect DB schema (spec already fixes DECIMAL(18,3)) or engine logic
  (comparisons work identically either way).
  Question: Should the UI enforce integer-only quantity input, or allow up to 3
  decimal places as the schema permits?
  Provisional assumption: allow decimals (matches schema as specified); no
  UI-side rounding/step restriction. Low-risk to change later since it's
  UI-only.

  O-03 — Target MSSQL instance
  Impact: determines connection string/config approach and whether the seed
  script needs a CREATE DATABASE step.
  Question: Is there an existing MSSQL server/database to point at, or should
  the seed/setup script create a fresh database?
  Provisional assumption: setup script creates the database if not present
  (idempotent IF NOT EXISTS), and connection details come from .env (NFR-06).
  This is the safer default for a from-scratch repo and doesn't preclude
  pointing at an existing instance later — just change the env vars.

  No other ambiguities materially change observable behavior — the spec is
  otherwise unusually precise (explicit tie-break rules, explicit inclusive
  boundary, explicit evaluation order, explicit HTTP codes for every path).

  Risks and deferred work

  - Row-locking approach unspecified: spec requires "locked or conditionally
    updated" inventory rows (FR-07, NFR-02) but doesn't pick a mechanism. MSSQL
    options: UPDLOCK, ROWLOCK hints in a SELECT ... FOR UPDATE-style pattern, or
    a conditional UPDATE ... WHERE available_quantity >= @qty with rowcount
    check. This is an implementation detail, not a requirement ambiguity —
    flagging so Slice 3 doesn't stall on it, recommend the
    conditional-UPDATE-with-rowcount-check approach since it needs no explicit
    transaction isolation-level tuning.
  - Order id format for validation (FR-02): "matches the allowed format and
    length" is stated but the format itself isn't pinned down beyond the example
    ORD-1001. Low risk — worth confirming a regex before Slice 3, but doesn't
    block earlier slices.
  - No auth (explicitly out of scope): fine for this release, but means the
    demo/test environment is the only environment this ships to as-is.
  - Deferred by spec, not by me: customer-type rules, partial/backorder
    fulfilment, replenishment, pricing/tax — all explicitly out of scope (§2.2),
    not reintroduced here.
  - Concurrency test tooling: E2E test suite will need a way to fire two
    truly-parallel requests (not just sequential awaits) to meaningfully
    exercise NFR-02 — worth deciding the test runner's concurrency primitive
    early in Slice 3 rather than retrofitting.

  Three open questions (O-01, O-02, O-03) are worth a quick confirmation before
  Slice 1/3 start, but none of my provisional assumptions block starting Slice 1
  or Slice 2 today.
